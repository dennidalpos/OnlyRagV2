# Runtime e orchestrazione Agent

Il flusso operativo è coordinato da [`agentOrchestratorAppService.ts`](../electron/core/application/agentOrchestratorAppService.ts). Il modello propone azioni; Main autorizza, esegue, verifica e stabilisce la chiusura.

Dependency verification scans each discovered Node project in an owned worker, with its existing 60-second deadline including queue/startup. Only one parser runs at a time, with bounded queued admission and heap/stack limits. Stop and shutdown cancel queued work and terminate the active scanner before accepting its result or admitting the next one. Missing/crashed/incomplete workers retain `unverifiable`; Main never parses as a fallback. [Implementation and qualification limits](./libraries.md#dependency-scanner-isolation--2026-10-10).

```text
Esegui -> collect_context -> propose_action -> apply_action -> verify -> outcome
Pianifica -> [interview -> request scope confirmation -> plan -> approval] -> run in selected mode
```

## Modalità operative

- **Ask**: strettamente read-only.
- **Guided** (default): richiede revisione e conferma per ogni mutazione (scrittura, rimozione, comandi shell).
- **Auto**: autorizza l'esecuzione autonoma locale; i gate per commit, installazione pacchetti e accesso di rete restano sempre attivi.
- **Full access**: disattivato per default; il profilo scelto viene salvato nel piano e nella run. In Guided e Auto consente file esterni al workspace e comandi/installazioni senza i gate applicativi, mentre Ask resta in sola lettura. Non modifica i privilegi del sistema operativo e gli effetti esterni non sono garantiti dal checkpoint. L'E2E Electron del 2026-09-28 ha verificato il piano `ready` riletto con il profilo, una scrittura esterna temporanea, un'installazione npm locale e il rifiuto della stessa scrittura senza Full access o in Ask.
- **Server di sviluppo gestito**: `start_dev_server` avvia soltanto lo script `dev` del `package.json` del workspace corrente in background. Main assegna `HOST=127.0.0.1` e una `PORT` libera; lo script deve ascoltare su quella coppia. L'avvio fallisce se la porta non si apre o se il listener è raggiungibile anche su un altro indirizzo locale. Il risultato indica la porta gestita; `probe_local_http` esegue GET soltanto su URL HTTP(S) loopback con quella porta e non segue redirect. `stop_dev_server` termina solo il processo avviato dall'app per quel workspace. Guided richiede conferma per avvio e arresto; Ask può soltanto eseguire la probe. L'app arresta i server gestiti alla chiusura.
- Richieste colloquiali di creazione (es. "fammi un sito") attivano gli strumenti di scrittura solo dietro approvazione in Guided; richieste di sola consultazione restano read-only.
- **Esegui** avvia sempre la run nella modalità selezionata. **Pianifica** è un'azione esplicita in Guided e Auto: apre l'eventuale intervista e il piano, richiede la conferma degli obblighi prima del piano e la sua approvazione prima dell’esecuzione nella modalità scelta. In Ask non è disponibile.
- Un cambio Ask/Guided/Auto durante una run aggiorna Main e vale dalla prossima azione. Il passaggio Guided → Auto risolve una conferma pendente dovuta solo alla revisione Guided; i consensi per rete, installazioni, comandi sensibili e commit restano richiesti. L'E2E Electron del 2026-09-28 verifica il passaggio Guided → Auto su una scrittura in attesa, il nuovo `num_ctx` nel turno Ollama successivo, il rifiuto degli aggiornamenti destinati a run in coda o concluse e la permanenza dei consensi di rete e installazione con Full access spento.
- File e terminale sono abilitati nelle nuove configurazioni; disattivazioni esplicite già salvate restano valide. La rete richiede approvazione per default e tutti i gate di sicurezza della run restano attivi.

## Pianificazione e intervista

- Intervista e generazione piano usano `/api/chat` con JSON Schema e `num_predict` calcolato sullo spazio libero residuo. La risposta arriva in streaming e viene ricomposta prima della validazione.
- Prima del piano, Main estrae un ledger della richiesta con ambito, destinatari e condizioni; il pannello richiede una conferma esplicita e consente correzioni. Poi [`planRequestCoverage.ts`](../electron/core/application/planRequestCoverage.ts) verifica riferimenti e insiemi dichiarati e confronta semanticamente i criteri originali con gli obblighi confermati. Il modello non può trasformare un obbligo in contesto. Una chiamata di estrazione precede al massimo due candidati e una revisione per candidato; nessun retry dell’estrazione, nessun piano prima della conferma. Timeout e budget dei candidati restano invariati. L’annullamento copre l’intera operazione e impedisce nuove chiamate nelle fasi successive. Questo è controllo del piano, non prova dell’implementazione.
- Per un workspace vuoto il piano deve rispettare gli entrypoint richiesti dallo scaffold. Se richiede `index.html` nella root e `src/main.*`, una proposta Create React App/`react-scripts` viene rigenerata tramite la correzione dello schema, salvo richiesta esplicita dell'utente. Un test mirato verifica il rifiuto e l'eccezione; la run live del primo prompt con `qwen3.5:4b` ha generato un piano React/Vite coerente, ma la qualifica complessiva resta aperta (5/9 milestone e runtime vuoto).
- `AgentPlan` strutturato (`formatVersion: 2`) è l'unica sorgente eseguibile; la resa Markdown è solo una vista per l'utente.
- Se il modello accetta solo livelli di reasoning (es. `gpt-oss:20b`), le richieste strutturate inviano il livello più basso riportato da `/api/show` (`resolveStructuredThinkValue` in [`ollamaThinkingPolicy.ts`](../shared/domain/agent/ollamaThinkingPolicy.ts)) per evitare payload vuoti con JSON Schema. Per un modello commutabile inviano `false` senza preferenza e, se l'utente ha scelto un livello (es. `low` per `qwen3.8:27b`), quel livello e non `true`, che applicherebbe il default del modello. La richiesta strutturata fallisce dopo 10 minuti senza output, cioè durante un caricamento bloccato o uno stream fermo (`ollamaHttpClient.generateStructuredNow`). La lunghezza resta limitata da `num_predict`, così un modello lento che ragiona a lungo non perde più il piano, come è successo due volte con qwen3.8:27b il 2026-09-26.
- Risposte strutturate invalide registrano `done_reason`, token impiegati e diagnostica dei delimitatori di testo.

## Ciclo di esecuzione

- Agent Coding richiede un modello installato che dichiari `tools` in Ollama. Ogni turno usa `/api/chat` con schemi nativi: Main conserva i messaggi `assistant` (contenuto, thinking e chiamate) e `tool`, esegue tutte le chiamate ricevute in ordine e restituisce ogni esito al modello prima della risposta successiva. Solo per `qwen2.5-coder:7b`, che su questa installazione ha restituito JSON nel contenuto pur dichiarando `tools`, un'intera risposta formata da un singolo oggetto `{ "name": ..., "arguments": ... }` viene validata contro gli schemi offerti e convertita in chiamata. Testo descrittivo, blocchi Markdown e strumenti non offerti non sono eseguiti; i consueti gate di sicurezza restano applicati.
- La prova desktop del 2026-09-29 con il primo blocco di `docs/prompt_test_sequenza.txt` conferma l'esecuzione di tool reali tramite questo recupero. Dopo 64 passi il modello aveva verificato 3/9 milestone; continuava però a tentare una build con un import Tailwind non esportato e a emettere talvolta JSON `update_plan` con `status: "blocked"`, conteggiato come `no_tool_detected` perché lo schema accetta `failed`. La descrizione dello strumento ora indica `failed` con la causa in `notes`; un test verifica che l'envelope JSON valida passi e `blocked` resti rifiutato. La run è stata annullata conservando checkpoint e file. La compatibilità del formato delle chiamate è verificata in live; la riuscita del task completo e l'effetto della descrizione corretta restano aperti.
- Una verifica fallita eseguita da `update_plan` restituisce anche il consiglio diagnostico prodotto dal medesimo analizzatore usato per `run_command`, mantenendolo come advice e senza promuovere la milestone. Per l'errore Webpack `"./tailwind.css" is not exported ... node_modules/tailwindcss`, il consiglio indica `grep_search` sull'import `tailwindcss/tailwind.css`, poi la correzione dell'integrazione CSS in base alla versione installata. Il test mirato conferma che il modello riceve questo feedback; l'effetto in una nuova run live resta da verificare.
- Per progetti web con `index.html` e script `dev`, il controllo di progetto avvia temporaneamente il server locale gestito e Chrome/Chromium headless. A 320, 375, 768, 1024, 1440 e 1920 px controlla errori JavaScript, contenuto visibile e overflow; se il piano li richiede controlla anche target tattili, navigazione Dashboard/Tasks e CSS compilato per Tailwind. Un build riuscito non verifica più le milestone di layout, navigazione o styling: serve la prova `web-ui smoke`. Il risultato fallito di una prova avviata dopo `run_command` torna nel messaggio tool dell'agente; `update_plan` e il gate finale rifiutano la promozione senza prova. I file UI dichiarati ma non raggiungibili dall'entrypoint e le directory di architettura nominate nei criteri restano residui. Se il browser non è disponibile, la verifica resta esplicitamente non confermata.
- Per esplorare l'app in modo interattivo, Agent Coding avvia prima `start_dev_server`, poi usa `browser_navigate` con un percorso locale, `browser_snapshot`, `browser_click`, `browser_fill` e `browser_screenshot`. Ogni run ha un contesto Chromium headless isolato, chiuso alla fine o all'annullamento. La pagina può raggiungere solo la porta del proprio server gestito: richieste verso altre origini, WebSocket esterni, popup, download e redirect HTTP sono bloccati. Questa eccezione di loopback è disponibile anche in `offline-strict`; Full access non la amplia. Ask consente solo navigazione e lettura; Guided chiede conferma per ogni clic o compilazione. Gli screenshot mascherano i campi editabili, restano in `.onlyrag/visual-validation/` e sono mostrati nella timeline tramite un IPC limitato a quegli artefatti. Lo snapshot omette i valori dei campi.
- Il modello può scegliere letture, modifiche, comandi e verifiche senza che una direttiva del piano restringa artificialmente il catalogo. Main applica comunque i controlli Ask/Guided/Auto, il confinamento del workspace, il consenso per rete e installazioni, le versioni dei file e il gate di chiusura basato su evidenze. `git_commit` viene esposto solo se richiesto nel task e richiede sempre conferma.
- Le risposte con più tool call vengono elaborate una alla volta. Una chiamata `finish` viene esaminata dopo le altre della stessa risposta. Il passo successivo parte solo dopo il risultato del passo precedente.
- Ogni chiamata riceve un messaggio `tool` con l'esito reale: motivo di un rifiuto (sicurezza, utente, policy, modalità), stato del piano dopo `update_plan`, errori di schema. Una risposta di sola prosa riceve il feedback come messaggio `user`, così la trascrizione non termina mai con un messaggio `assistant`. Output troncato (`done_reason=length`) o argomenti non JSON tornano al modello come feedback invece di un nuovo tentativo identico.
- Solo `planDirectiveArbiter.ts` emette ordini, al massimo uno per turno e mai per un tool che la capability policy rifiuta; gli altri controlli restituiscono fatti consultivi nel risultato del tool.
- Le diagnostiche descrivono la correzione come dato (`DiagnosticAdvice` in [`diagnosticAdvice.ts`](../electron/core/domain/agent/diagnosticAdvice.ts)): nel risultato del tool diventa un consiglio (`renderAdvice`, sezione "Suggested fix"), e solo l'arbitro la trasforma nell'ordine del turno (`renderOrder`, "Directives:" / "MUST"). L'arbitro rilegge i consigli salvati nella trascrizione con `parseRenderedAdvice`. Anche il comando iniziale imposto dall'utente è una sua decisione (`user_first_command`). Dettagli e invariante di test in [agent-guards.md](agent-guards.md#consigli-e-ordini).

## Confinamento e workspace

Project verification requires a terminating command for every discovered project. Each discovered `package.json` receives its own dependency scan before commands run, using that package's manifest and paths; a root scan cannot cover a nested package. Unavailable scans, inaccessible directories, unparseable source files or unreadable installed peer declarations produce `unverifiable`, not a clean result. Missing installed provider manifests remain tolerated only on `ENOENT`. Scanner deadlines are cleared after success/failure; the existing 60-second deadline includes queueing and worker startup. Parser work runs in a dedicated worker; timeout and cancellation terminate that owned worker and refuse verification.

Cancellation is checked after dependency scans, command settlement and browser verification before success can be reported. Discovered non-Node projects currently have no native command resolver, so they remain explicitly unverifiable rather than inheriting a Node project's success. `PROJECT-VERIFICATION-COMMAND-COVERAGE-01` tracks that command-discovery limitation; worker isolation is verified separately; upstream braces remediation remains tracked. [Verification and scope](./verification.md#dependency-verification-completeness--2026-10-06).

- **Run di progetto**: opera direttamente nel workspace dell'utente, con i suoi `node_modules`, il piano approvato e lo stato di sessione. Prima della prima run l'app crea `.onlyrag/` anche in un workspace vuoto, con un `.gitignore` interno che la esclude da Git. I tool file dell'agente non possono leggere o modificare questa cartella; i comandi shell arbitrari conservano le protezioni esistenti. Il journal registra lo stato precedente di ogni file modificato dai tool; a fine run, anche per annullamento o timeout, diventa un checkpoint in `.onlyrag/checkpoints/<id>` ([`agentCheckpointStore.ts`](../electron/core/infrastructure/filesystem/agentCheckpointStore.ts)) e le modifiche restano sul disco. Il manifest registra la chat proprietaria. Il ripristino è un'azione esplicita dell'utente (`agent:restore-checkpoint`, pulsante nella scheda di evidenza). Gli effetti dei comandi shell (installazioni, generatori) non sono nel checkpoint e compaiono tra gli effetti esterni.
- La scoperta dei progetti ignora le cartelle di cache di pytest, oltre a build, dipendenze e ambienti virtuali: una cache non accessibile non interrompe il piano.
- **Standalone**: confinato in `userData/agent-scratch` (`userdata_dev/agent-scratch` senza Electron, mai la cartella home), persistente tra sessioni e gestibile da UI (Mostra, Esporta, Svuota). Le run senza workspace valido sono rifiutate senza ricadere nella cartella di installazione o in `process.cwd()`.

## Contesto, token e thinking

- **Prefisso stabile**: la richiesta è `[system, task, ...trascrizione, contesto del turno]`. Il messaggio `system` viene composto una volta per sessione e il task compare una sola volta come primo messaggio `user`; passo, stato del piano, direttiva ed errori stanno nell'ultimo messaggio `user`, effimero. Ollama riusa la cache KV solo sul prefisso comune fra richieste consecutive, quindi ogni turno rivaluta solo le novità ([`agentChatTranscript.ts`](../electron/core/application/agentChatTranscript.ts)).
- **Follow-up**: una nuova run nella stessa conversazione conserva la trascrizione; il primo messaggio `user` resta il task iniziale della conversazione e la nuova richiesta viene aggiunta una volta in coda. Modello e `num_ctx` fissati da una run valgono solo per la sua ripresa: un follow-up usa le impostazioni correnti ([`agentOrchestratorSessionContext.ts`](../electron/core/application/agentOrchestratorSessionContext.ts)).
- **Misuratore Ctx**: misura i messaggi realmente inviati più gli schemi tool; confronta la stessa somma con `prompt_eval_count` riportato da Ollama e corregge al rialzo il budget del turno successivo. Anche la compattazione usa il rapporto calibrato. Le sequenze di almeno 512 caratteri identici si contano con il rapporto prudente di 3,5 caratteri per token invece del BPE, quadratico su di esse ([`contextWindowCalculator.ts`](../shared/domain/agent/contextWindowCalculator.ts)).
- **Finestra di contesto**: `num_ctx` rispetta il limite dell'hardware (`hardwareProfileResolver.ts`), con 65536 token per l'agente su host con almeno 32 GB di RAM (Ollama raccomanda almeno 64000 token per agenti e coding), e il massimo dichiarato dal modello. `num_predict` occupa lo spazio residuo della finestra; almeno un quarto della finestra (2k-16k token) resta riservato alla risposta.
- Il Ctx scelto per il modello in Gestione Modelli Ollama viene inviato con `num_ctx` a `/api/chat`. Se cambia durante una run, Main applica il nuovo valore dalla prossima richiesta al modello, ricalcola i budget collegati e lo limita al massimo dichiarato dal modello. La richiesta già in corso mantiene il valore precedente.
- **Campionamento**: l'agente non invia `temperature`, `top_p`, `top_k`, `repeat_penalty`, `num_thread` né stop sequence; valgono i default del Modelfile e i core fisici scelti da Ollama. `modelSamplingOverrides` permette un override per modello, modificabile nella scheda del modello in Impostazioni (Campionamento) ([`ollamaSamplingOptions.ts`](../shared/domain/agent/ollamaSamplingOptions.ts)).
- **Compattazione**: quando la trascrizione supera il budget, gli scambi più vecchi vengono rimossi fino al 70% del budget in un solo passo, così la cache resta valida fra un taglio e il successivo. Se anche l'ultimo scambio assistente/tool non entra, viene rimosso intero senza lasciare risultati tool orfani; il task iniziale e il contesto corrente restano. La modalità `Compact` tenta prima di conservare l'ultimo scambio. La timeline di audit rimane intatta. La prova live a 16K con `qwen3.5:4b` del 2026-09-28 ha raggiunto 50/50 turni senza il precedente overflow al turno 17; la run è poi terminata per `step_budget` con 3/9 milestone verificate e build fallita.
- **Thinking**: preferenze per singolo modello (`ollamaThinkingPolicy.ts`), con i livelli letti da `/api/show`. Senza preferenza l'agente omette `think` e Ollama applica il default del modello; la UI offre "Predefinito del modello", "Spento" (se il modello lo consente) e i livelli riportati. Chat e traduzione (anche quella in-place della Sidecar) restano senza thinking finché l'utente non lo attiva; se ha scelto un livello, inviano quel livello e non `true` (`chosenThinkValue`).

## Sessione, identità e audit

- Il caricamento dello stato agente restituisce assenza solo per file mancanti (`ENOENT`). JSON invalido, record incompleti, identità incoerenti o letture indisponibili bloccano seed, ripresa e scritture dipendenti conservando i dati originali. L'avvio segnala `blocked` prima di chiamare il modello e libera la run; l'approvazione resta riprovabile dopo il recupero dello storage. I seed legacy validi senza identità di run e la normalizzazione dei vecchi modi a Guided restano compatibili. Il debug bundle propaga l'errore invece di presentare una traiettoria vuota. Nessun ripristino automatico di checkpoint o nuovo formato persistito; [prove e limiti](./verification.md#agent-state-preservation--2026-10-06).

- Le milestone operative avanzano nell'ordine del piano: una voce resta attiva fino alla verifica o all'abbandono, poi la run prosegue automaticamente con la successiva. Una scrittura o una verifica non attiva più voci insieme; la checklist mostra una sola voce "IN CORSO". L'E2E Electron del 2026-09-28 ripristina due voci `in_progress`, rifiuta la verifica anticipata della seconda e conferma che la seconda resta attiva dopo la verifica della prima; il server Ollama della fixture è simulato.
- Ogni comando ed evento trasporta l'identità immutabile `{ runId, conversationId, planRevisionId, workspaceId }`. Il Renderer accetta solo eventi della run attiva.
- Timeout e annullamento condividono un `AbortSignal`; la cancellazione blocca l'elaborazione di eventi successivi. Nessuno dei due annulla le modifiche: entrambi salvano il checkpoint e il timeout notifica la fine della run al Renderer.
- Il timeout predefinito della sessione è 120 minuti, configurabile nelle impostazioni. Prima degli header HTTP, il trasporto attende almeno 10 minuti e, se maggiore, usa il limite di silenzio adattivo calcolato dalla velocità misurata nella sessione. Lo stesso limite adattivo vale dopo gli header (il tempo per circa 4096 token, fra 5 e 30 minuti), perché Ollama può trattenere una tool call fino al completamento. Il timeout iniziale indica assenza di risposta HTTP, non necessariamente caricamento del modello.
- **Budget di ragionamento**: un turno può ragionare al massimo per un decimo del timeout di sessione, fra 5 e 30 minuti (`reasoningBudgetMs` in [`agentOrchestratorTurnDispatch.ts`](../electron/core/application/agentOrchestratorTurnDispatch.ts)), prima di produrre testo o una tool call. Oltre il limite il trasporto chiude la richiesta e Ollama smette di generare. Il ragionamento tagliato non entra nella trascrizione, e il modello riceve un feedback che chiede il prossimo passo con un ragionamento breve. Il silenzio che segue il ragionamento, mentre Ollama compone una tool call, non conta. Due tagli nello stesso turno chiudono la run con `transport_budget`. Il limite nasce da un turno di qwen3.8:27b che ha ragionato per 159 dei 180 minuti di sessione.
- Il layout locale è identificato da `<workspace>/.onlyrag/layout.json` (versione 2). Lo storico è in `sessions/history.json`; ogni chat usa `sessions/<sha256(sessionId)>/state.json` e `SESSION_TRACKER.md`. Restano `checkpoints/`, `artifacts/` e `visual-validation/`. Senza un workspace utilizzabile lo stato continua a usare `userData/sessions` (`userdata_dev/sessions` senza Electron) ([`userDataRoot.ts`](../electron/core/infrastructure/filesystem/userDataRoot.ts)). Al primo accesso al vecchio layout l'app crea `migration-backup/v1`, copia e verifica i dati prima di eliminare i vecchi file, e può riprendere dopo un'interruzione. Il vecchio tracker unico viene assegnato solo se si identifica una sola chat; altrimenti resta in `legacy-unassigned/SESSION_TRACKER.md`.
- L'E2E Electron del 2026-09-28 ha verificato in un profilo isolato l'inizializzazione del layout prima della run, la migrazione di una chat legacy sintetica con rilettura e backup, la cancellazione di una sola chat e la rimozione/riapertura del progetto senza perdita di dati.
- Il tracker per chat usa il formato 2 con sezioni stabili `completed_tasks`, `modified_files`, `unresolved_issues` e `next_steps`. Le intestazioni sono identificatori indipendenti dalla lingua dell'interfaccia. Nei turni `focus` il blocco della chat viene riletto dal disco e inserito nel contesto variabile del turno; il messaggio di sistema resta congelato per conservare la cache del prompt. L'E2E Electron del 2026-09-28 verifica che un problema esplicito segnato durante la run appaia nel successivo prompt `focus`; `open_milestones` è solo un conteggio di stato e il parser lo esclude dai problemi. Il parser legge anche il vecchio formato numerato in inglese; il riepilogo della chiusura viene costruito dai dati del tracker tramite le chiavi localizzate `closure*`. Quando un guard ferma la run, usa questo stesso riepilogo e non aggiunge una seconda sintesi italiana fissa. La cancellazione di una chat rimuove il suo stato, tracker e checkpoint attribuibili. Rimuovere un progetto dall'elenco lascia intatti i dati locali, disponibili alla riapertura.
- La compatibilità per seed di piano senza identità e sessioni standalone nel fallback resta attiva. Il 2026-09-29 il registro dell'app aveva un progetto (`Desktop/test_app`) con `sessions/history.json` nel layout attuale e nessun file di stato/storico legacy; il fallback dell'app aveva 0 sessioni e 0 stati legacy. `userdata_dev` aveva 0 sessioni fallback ma 21 file `.agent_state_*.json` leggibili, tutti con `workspacePath: null` e `runIdentity`, da conservare finché non se ne chiarisce la provenienza. Il progetto registrato è un riferimento di regressione in sola lettura, non un corpus legacy reale che consenta di rimuovere la compatibilità. Prima di eliminare questi rami serve una release che migri un corpus legacy non vuoto con backup e rilettura verificati, seguita da un nuovo inventario di workspace e fallback senza record residui.
- Quando tutte le milestone operative sono verificate e non restano tool call pendenti, l'applicazione esegue direttamente il gate finale di evidenza, anche all'ultimo step disponibile. Alla chiusura dopo il limite di passi, il runner di verifica conserva l'etichetta leggibile del progetto (per esempio `.: npm run build`) e passa separatamente il comando effettivo (`npm run build`) alla promozione delle milestone: un controllo finale riuscito accredita quindi la milestone corretta, mentre il guard `step_budget` mantiene la run nello stato bloccato. Non attende un turno LLM dedicato al solo riepilogo: la run live qwen3.8:27b del 2026-09-27 aveva verificato 8/8 milestone e superato build e test, ma quel turno aggiuntivo si è fermato dopo due timeout di 10 minuti (`transport_budget`). Il successivo run `closure-20260927` si è fermato con 0/8 milestone dopo un build fallito e due timeout iniziali, quindi non ha ancora confermato questa chiusura in live.
- La run live del 2026-09-27 ha esercitato le direttive riviste su un task completo: 8/8 milestone verificate, due consigli `execution_budget` seguiti da prosecuzione, senza ordini concorrenti osservati. La richiesta di preview è stata bloccata dalla policy di rete, senza impedire build e test. Questo chiude la verifica live di AGENT-DIRECTIVE-AUTHORITY-03.
- La trascrizione nativa viene salvata con lo stato della sessione. Dopo un'interruzione, le chiamate rimaste senza risultato sono marcate come non eseguite prima di riprendere la conversazione.
- Al completamento, la timeline espone evidenze persistite: file modificati, esito dell'ultima verifica ed eventuali effetti esterni.
