# Specifica Tecnica: Infrastruttura di Audit e Ottimizzazione Universale dei Prompt per OnlyRag V2

## 1. Ambito d'Applicazione (Scope & Domain)
L'ambito esclusivo di questa infrastruttura è l'LLMOps e il Testing di Regressione Semantica per Agenti AI Autonomi di Sviluppo Software (Coding Agent Studio) funzionanti in ambienti locali e vincolati.

### Obiettivo dell'Audit
Garantire che una suite fissa e immutabile di prompt utente produca un comportamento dell'agente deterministico, sicuro e corretto. Il sistema deve funzionare in modo universale su qualsiasi tipologia di progetto software (agnosticismo dello stack) ed essere resiliente ai limiti cognitivi intrinseci dei modelli Small Language Model (SLM) locali (es. 7B/14B non aggiornati o privi di capacità di ragionamento nativo).

---

## 2. Stack Tecnologico Proposto (Target Toolchain)

Per l'implementazione e l'esecuzione dell'audit, lo stack è rigorosamente suddiviso per layer architetturali, integrandosi con la Clean Architecture esistente del progetto:

LAYER 1: TESTING ENGINE & EVALUATION MATRIX
• Promptfoo (CLI & Core Runner)
• Pytest (Test Runner per l'Infrastruttura del Sidecar Python)

LAYER 2: RUNTIME OBSERVABILITY & TRACING
• Langfuse SDK (Open-Source LLM Tracing - Node.js Core & Python Sidecar)

LAYER 3: COGNITIVE EVALUATORS & JUDGES
• DeepEval / Ragas (Framework di validazione metrica basata su LLM)

---

## 3. Flusso Logico End-to-End (Operational Workflow)

Il flusso si esegue in modo sequenziale e ciclico ad ogni mutazione dei prompt di sistema o del motore di orchestrazione:

[1. Ispezione & Setup Sandbox] ──> [2. Consolidamento & Riconciliazione]
                                                   │
                                                   ▼
[4. Valutazione Metrica Visiva] ◄── [3. Esecuzione & Tracing in Cascata]

### Fase 1: Ispezione e Setup della Sandbox (Environment Discovery)
1. Lo script di automazione inizializza una directory di test isolata (Sandbox).
2. Il sistema esegue il probe dell'ambiente (projectStackDetectionRepository.ts) e classifica la cartella in due stati mutuamente esclusivi:
   * Stato A (Progetto Vuoto): Cartella priva di manifest o file sorgente.
   * Stato B (Progetto Esistente): Presenza di codice pregresso, debiti tecnici o strutture predefinite.
3. Se viene rilevato lo Stato B, il modulo compactSemanticRepoMapper.ts esegue una scansione AST immediata per estrarre l'albero dei simboli esportati prima di generare qualsiasi prompt.

### Fase 2: Consolidamento e Riconciliazione del Piano (Context Assembly)
1. Il GoalDecompositionPlanner.ts esegue il modulo workspaceDeliverableProbe.ts sulla sandbox.
2. I file già esistenti su disco che contengono codice reale vengono mappati: le milestone associate a tali deliverable vengono automaticamente promosse a uno stato avanzato (in_progress o pronti per la verifica), impedendo riscritture da zero o runaway loops di scaffolding (es. sovrascritture di file configurati).
3. L'orchestratore estrae i milestone residui non verificati della sessione precedente ed esegue il Consolidamento Automatico del Residuo, iniettandoli come contesto nel prompt per l'SLM.

### Fase 3: Esecuzione del Tool Loop e Tracing in Cascata (Execution & Telemetry)
1. La suite fissa di prompt viene inviata all'orchestratore tramite l'endpoint del provider (Promptfoo CLI).
2. Durante l'esecuzione del ciclo agentico, l'SDK di tracciamento (Langfuse) intercetta e registra in tempo reale ogni singola transazione (Span):
   * RAG Context Retrieval Time (Efficienza delle query su LanceDB).
   * Token Usage & Generation Latency (Ollama Rest API).
   * Tool Fingerprinting & State Tracking (AgentActionLoopDetector).
3. Se l'SLM genera un output non strutturato (JSON malformato o troncato a causa di limiti di contesto), interviene il toolParser.ts a livello infrastrutturale che ripara la sintassi tramite passaggi deterministici ed estrae il blocco bilanciato ottimale, neutralizzando i deficit cognitivi del modelo locale.
4. In caso di errore del terminale o di compilazione, il DiagnosticOutputReducer intercetta l'output, lo depura dai codici ANSI, isola esclusivamente lo stack trace rilevante e lo reinvia come prompt di auto-healing, forzando la compressione del contesto.

### Fase 4: Valutazione Metrica e Verdetto (Evaluation Gate)
1. Al completamento del task (o al raggiungimento dei circuit breaker di stagnazione), l'interfaccia di valutazione (DeepEval/Ragas) analizza la traiettoria finale rispetto alla suite fissa di test case.
2. Vengono estratti i verdetti basati su metriche matematiche e semantiche rigorose:
   * Answer Relevancy: Pertinenza della risposta rispetto all'input iniziale.
   * Faithfulness / Hallucination Detection: Assenza di codice o asserzioni non supportate dal contesto RAG o dalle skill.
   * Tool Call Accuracy: Correttezza sintattica ed esecuzione della sequenza minima di strumenti per risolvere il task.
3. Se una metrica scende sotto la soglia stabilita, il test fallisce e viene generato un report diagnostico in Markdown esportabile.

## 4. Matrice dei Criteri di Accettazione per l'Agente di Audit (DoD per l'AI)

L'agente AI incaricato dell'audit e della validazione di questa infrastruttura deve verificare il rispetto assoluto dei seguenti vincoli architetturali:

* Agnosticismo Sintattico: L'infrastruttura di test non deve contenere comandi CLI specifici di un linguaggio cablati nei test case principali. I test devono interfacciarsi esclusivamente con i tool astratti dell'orchestratore (run_tests, read_file, replace_file_content).
* Isolamento dei Livelli (Clean Architecture): I moduli di valutazione semantica (LLM come giudice) devono risiedere esclusivamente nei file di test esterni o nel Sidecar Python (sidecar/tests/). Il Domain Layer di Electron non deve avere dipendenze dirette dalle librerie di testing.
* Anti-Hardcoding sui Modelli: I file di configurazione dei test non devono assumere che il modello locale possieda informazioni aggiornate sugli stack di mercato. Qualsiasi informazione contestuale sulle dipendenze deve essere estratta a runtime dai manifest reali del workspace e iniettata dinamicamente nel prompt di sistema tramite variabili di template.
* Idempotenza della Sandbox: Ogni ciclo di test eseguito sulla suite fissa di prompt deve rigenerare o pulire atomicamente lo stato della sandbox (tramite le fixture dell'ambiente), garantendo che i test su progetti esistenti non siano corrotti da esecuzioni precedenti.
