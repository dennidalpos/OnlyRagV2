## Bounded tabular reads — 2026-10-11

### Opt-in Excel format dimensions — 2026-10-11

Settings exposes **Excel: format dimensions**, off by default. When enabled for an ingestion request, `.xls` accepts coordinates up to 65,536 rows × 256 columns and `.xlsx` up to 1,048,576 × 16,384. The 8 MiB `.xls` source and 16 MiB uncompressed `.xlsx` shared-string parser refusals remain the default policy; this opt-in bypasses those two parser limits. The existing 512 MiB source-file admission and extraction/storage gates still apply, and available memory can prevent a dense workbook at the geometric maximum from completing. [Microsoft's current Excel limits](https://support.microsoft.com/en-us/excel/excel-specifications-and-limits) and [legacy worksheet compatibility](https://support.microsoft.com/en-us/excel/worksheet-compatibility-issues) define the coordinates; [xlrd on-demand behavior](https://xlrd.readthedocs.io/en/latest/on_demand.html) explains why one selected `.xls` sheet still occupies memory.

For opt-in workbooks, the RAG Markdown contains at most the first 150 nonempty rows and 128 nonempty columns per selected sheet, with each displayed cell limited to 256 characters. `Row` and `Col N` preserve source coordinates, including sparse cells at the final format coordinate. Notes state the total nonempty rows/columns, omitted columns and shortened cells. The first 10 sheets remain selected by default; the original file is retained. This is a bounded retrieval excerpt, not a complete workbook index. The 2026-10-12 adversarial desktop qualification below covers XLSX; full-format XLS native materialization remains in `XLS-FULL-FORMAT-NATIVE-BOUND-01`.

CSV/TSV uses 1,024-row pandas chunks with literal string cells, counts blank data rows and drains the entire parser to catch malformed rows after the displayed limit. Parquet uses Arrow batches of at most 1,024 rows without pre-buffering, checks the scanned count against file metadata and retains only displayed rows. XLSX uses openpyxl read-only iteration over selected sheets, counts rows even past the displayed range and reports selected sheets without readable cells. XLS uses xlrd on-demand sheets, unloading each after conversion. It still materializes one selected sheet, so sources above 8 MiB are refused before parsing. XLSX shared-string XML above 16 MiB uncompressed is also refused before openpyxl loads it. Existing configured row/sheet limits remain; omitted row and sheet counts appear in the extracted Markdown. A selected range with no readable cells fails before indexing. Original files are untouched.

On this Windows host, 200,000-row CSV (2.49 MB) and Parquet (1.14 MB), and 20,000-row XLSX (0.21 MB) fixtures rendered 300 rows with correct total counts. Parser Python-allocation peaks measured with `tracemalloc` were 1.2, 2.0 and 3.6 MiB; process peak working sets, including fixture construction and imports, were 135.1, 141.5 and 134.0 MiB. These are declared-workload measurements, not a bound for arbitrary column widths or compressed cell payloads. Source bytes are still subject to the existing 512 MiB file gate; this change bounds additional table materialization, not the incoming source buffer. The wide/compressed payload follow-up completed at the declared 2026-10-12 boundary below. [Focused verification](./verification.md#bounded-tabular-reads--2026-10-11).

Parser contracts checked 2026-10-11: [pandas chunked CSV and bad-line handling](https://pandas.pydata.org/docs/reference/api/pandas.read_csv.html), [Arrow Parquet batches](https://arrow.apache.org/docs/python/generated/pyarrow.parquet.ParquetFile.html), [openpyxl read-only worksheets](https://openpyxl.readthedocs.io/en/stable/optimized.html), [xlrd on-demand sheets](https://xlrd.readthedocs.io/en/latest/on_demand.html). The 2026-10-12 adversarial limits below supersede the earlier 1,024-row chunk and batch sizes.

### Prompt-session deletion fence — 2026-10-11

The approved `/history/remove` extension accepts a bounded `operation_id` with `session_ids`; `restore=true` explicitly reactivates only sessions retained under that operation. A version-1 `prompt_session_lifecycle` table records each session's state, operation and generation. Deletion writes the fence before removing prompt rows. An index call checks the generation before embedding and again under the database gate before append, so a worker released after deletion or restore cannot reintroduce an old row. Duplicate removal and restore for the same operation are idempotent; mismatched restores and corrupt lifecycle rows refuse. Search excludes fenced rows if row removal failed. Existing project-only removal keeps its previous contract. This extension does not restore prompt content; Main must retain and explicitly reindex it as part of the still-open deletion recovery task. No personal store was changed. [Focused verification](./verification.md#sidecar-session-deletion-fence--2026-10-11).

### Independent lexical retrieval — 2026-10-02

The final focused FTS/Sidecar run passes 69 tests in 15.61s.
