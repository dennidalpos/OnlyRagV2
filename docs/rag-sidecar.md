## Claim/source provenance — 2026-10-02

`RAG-CLAIM-SOURCE-PROVENANCE-01` implements the conservative location/reference policy approved by the user on 2026-10-02. Previously chunks had no source offsets and ingestion retained only the caller's path. The old page preview can still fall back to rendered Markdown, so it is not used to verify citations.

Approved boundary:

- Retain an immutable original under the gated app document root for new ingestion, with a SHA-256 revision identity. Preserve raw extraction separately from normalized/edited Markdown. Original page/section positions refer to that retained extraction; offsets in edited Markdown must never be relabeled as original positions.
- Add optional versioned provenance to search results: `source_revision`, `extraction_revision`, `page_number`, `section_header`, `span_start`, `span_end`, `exact_quote`, and `location_kind` (`original`, `derived`, `unavailable`). Character offsets are zero-based Unicode code points, end-exclusive, with a documented representation hash. Unresolvable or ambiguous transformations retain only the known page/section and explicitly lack an exact original span. Identity joins use `doc_id` and revision, never filenames.
- Extend shared search/citation types and Main response validation; generated REST OpenAPI derives from Sidecar schemas. Existing callers accept absent provenance as unavailable. Existing stores remain readable; no vector-space migration, automatic personal reindexing or embedding rebuild is introduced by this approval.
- Add a gated `ingest:source-location` invoke and authenticated `GET /documents/{doc_id}/source-location` with revision and bounded page/span selectors. Resolve through stored IDs inside the app root; reject stale revisions, missing originals, invalid spans and paths supplied by a model. Return verified location metadata and either an original page preview or a bounded exact-text excerpt. Derived preview fallback stays separately labeled.
- Give each supplied passage a turn-local reference such as `[S1]`, bound to the exact body actually sent after context truncation. Parse answer references after generation and keep cited passages separate from uncited retrieval candidates. Unsupported, unknown, stale, cancelled or unsupplied references never acquire a verified-location badge. Label a valid citation as a model-cited passage with a verified location: reference validation alone does not prove that the passage entails the claim.
- Extend chat persistence additively with revision-bound references and citation state; old conversations retain candidate-only cards. Verify new ingestion, replacement, deletion, cancellation, repeated filenames, non-BMP characters, late PDF pages, normalization/edit ambiguity and stale historical references on isolated stores. Independently review claim support on a frozen corpus before closing F11. Retain backup/readback/rollback evidence before any existing personal-store migration; that remains separately unauthorized.

Example: an answer saying "Payment is due within 21 days [S2]" opens the retained original page/section for the exact `[S2]` passage. `[S99]` is visibly unresolved. If `[S2]` exists but says 30 days, its location can be verified while the claim remains unsupported; mechanical reference checks must not certify that answer.

The selector/revision design follows the [W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/#selectors), checked 2026-10-02; this is a local policy, not the full standard. Implementation uses additive `provenance` objects and version-1 `extraction.json` archives under `<userData>/data/source-documents/<doc_id>`, without changing vector/document table schemas or the recovery journal. Originals are copied/hash-checked in 1 MiB blocks before extraction (512 MiB limit); raw extraction is bounded to 10 million code points/10,000 pages. Existing records remain candidate-only without an archive. Unique exact raw-extraction matches carry code-point spans and known PDF/image pages; repeated or rewritten text is derived, with no fabricated original span. Section identity is omitted if the indexed representation changed; DOCX/text/tabular extraction does not invent original pagination.

Source navigation resolves current document/chunk identity, all three revisions and the original span, checks the retained file hash and returns its exact extraction excerpt plus a real original PDF page image when available (16 million pixel limit). There is no derived-preview fallback. Main validates responses against the requested identity. Truncated supplied passages shorten the original span safely. Streaming, cancelled and failed turns retain candidate states; only completed turns mark references actually present in the answer as model-cited. Opening verifies a location, never semantic entailment. Chat adds optional fields and revalidates on navigation; old conversations remain intact.

Native/DOM checks and four independently reviewed real-9B cases with captured real Nomic retrieval: [verification](./verification.md#claimsource-provenance--2026-10-02). Broader semantic/desktop qualification, English response consistency, archive lifecycle/backup/export and retrieval metadata cost remain tracked. No personal store was migrated; embedding rebuild remains deferred.

### Common ingestion context and normalization budgets — 2026-10-05

The user approved one common `numCtx` / `num_ctx` for Vision OCR and optional normalization, with no new request field. Both PDF extraction paths and image extraction pass it through. Streaming PDF previously omitted it when preparing page work items; that also dropped the requested Vision context. Normalization now sends the selected `num_ctx` explicitly, instead of inheriting Ollama's host default. A normalization-eligible page without a valid selected context produces `context_missing` and retains the complete original for review. Short/non-normalized pages retain their existing behavior. Callers must choose a window suitable for both selected roles; the shipped UI still disables LLM normalization and preserves its hardware/model context resolution.

Admission conservatively counts the full prompt's UTF-8 bytes plus 128 units for template framing, reserves the original text's UTF-8 bytes plus 64 for output, and caps `num_predict` at the existing **2048** maximum. The selected context bounds input plus output; insufficient space produces `context_budget_exceeded` before generation. There is no source slicing or context increase. This is a conservative byte admission policy, not an exact tokenizer or arbitrary custom-template certification. Larger Unicode pages can require review even if native tokenization would fit; qualification of false refusals/custom templates remains in the existing content/model qualification tasks. Thinking can exhaust the same bounded output; incomplete output still requires review. The normalizer's **25-second** timeout and existing retries/workers are unchanged.

The existing original-preserving non-indexed review carries both localized reasons through Main/IPC. No persisted status, migration, schema column, dependency, automatic acceptance relaxation or UI activation was added. `.venv\Scripts\python.exe scripts/live/normalizationContext.py` captures two complete real 9B requests on the unchanged frozen corpus with `num_ctx=4096`, `num_predict=2048`, thinking false and the existing timeout. ### Independent lexical retrieval — 2026-10-02

`RAG-INDEPENDENT-LEXICAL-RETRIEVAL-01` is complete. Native LanceDB FTS retrieves candidates independently of the dense shortlist, with the same prefiltered document selection. The union enters RRF (`k=60`); ties are deterministic by chunk ID. Each returned candidate retains dense rank (possibly absent), lexical rank, BM25 score, raw RRF score, fused rank and final rank in DEBUG diagnostics. The existing REST/IPC result shape remains unchanged; its `score` is an uncalibrated ranking heuristic, not evidence confidence. Score meaning and evaluated abstention are documented below; source provenance remains open.

The final lexical heuristic also considers filename/header matches and retains short identifiers. Fixtures give the exact evidence an ID that loses alphabetical ties to unrelated dense candidates: successful retrieval must depend on content/metadata, not favorable IDs. ## Dati e lifecycle

- Tabelle e filtri sono gestiti da [`sidecar/infrastructure/db.py`](../sidecar/infrastructure/db.py).
- Il Main avvia e arresta il processo tramite `sidecarProcessManager`, passando `OLLAMA_BASE_URL` (dal setting `ollamaHost`) e un token di sessione; cambiare host Ollama riavvia il Sidecar.
- In sviluppo, `npm run dev` avvia Electron e il Sidecar con i dati dell'app. `ONLYRAG_E2E_TEST=1` è riservato ai test isolati: disabilita deliberatamente l'avvio del Sidecar e mostra il vector DB come `offline`. Per controllare l'avvio normale, lasciare non impostata quella variabile e interrogare `http://127.0.0.1:8000/health`. Il 2026-09-29 l'avvio dev normale ha raggiunto `Sidecar: online` dopo l'inizializzazione di Python e `/health` ha risposto con FastAPI/LanceDB 2.5.0.
- Il database persistente vive in `<userData>/data/lancedb_store`.
- Il vecchio comando `scripts/migrate_chunk_context.py` aggiorna solo i prefissi di contesto, non introduce provenienza/dimensioni versionate ed è una migrazione storica. Non usarlo per aggiornare il nuovo indice o qualificare dati legacy. La ricostruzione completa con backup/readback/rollback è ancora tracciata in `RAG-EMBEDDING-REBUILD-01`; le prove storiche successive non la sostituiscono.
- Prova live isolata del 2026-09-27: indice LanceDB con un chunk legacy e uno corrente, entrambi con `nomic-embed-text` generato da Ollama. La preview ha contato 1 chunk; `--apply` ne ha convertito 1. Il vettore risultante coincide con un nuovo embedding Ollama, tutti gli altri metadati e il chunk corrente sono rimasti identici, il backup era leggibile e il suo ripristino offline ha recuperato le righe originali. La preview del 2026-09-29 sul `userData` reale ha ancora riportato `No chunks table; 0 chunks need migration`; la prova su corpus reale resta aperta.
- Durante l'avvio il Renderer ripete la diagnostica ogni secondo finché il Sidecar non risponde, poi torna all'intervallo ordinario di 10 secondi. Il primo controllo `offline` non viene quindi mantenuto mentre LanceDB sta ancora inizializzando.
- Lo stderr del processo viene classificato dal contenuto: le righe `INFO:` di Uvicorn restano informative, mentre `WARNING:`, `ERROR:`, `CRITICAL:` e traceback mantengono una severità operativa.
- I residui su `:8000` sono reclamati solo se il processo appartiene ai binari autorizzati.
- Il vocabolario aggiuntivo viene solo dagli asset inclusi nel Sidecar (`sidecar/assets/vocab/manifest.json` e i pack che elenca): all'avvio `VocabSyncService` copia nella cache, con sostituzione atomica, i pack la cui versione è cambiata. Nessun accesso di rete; un manifest illeggibile conserva la cache esistente.
- `/ingest-path-stream` riceve un path validato dal Main e conserva una copia/hash del sorgente per le nuove ingestion prima dell'estrazione; il file del chiamante resta invariato. L'archivio non viene eliminato automaticamente con il documento, né dopo rifiuti, cancellazioni o rollback: gestione e backup/export sono tracciati in `SOURCE-ARCHIVE-LIFECYCLE-01`. Un archivio senza record/chunk validi resta non navigabile.
